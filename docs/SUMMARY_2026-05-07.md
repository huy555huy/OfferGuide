## 一句话结论

**战略对、SKILL 真行、产品壳烂、agent 太内向。**

把产品壳和 agent 性补上，OfferGuide 就从"Anthropic 风格的求职后台"变成"真的可以日用的求职 copilot"。

---

## 三个核心判断

### ① 战略押在了对的地方 ✅

不替你点投递、做投前决策辅助 + 投后追踪——这条路在 2026 年是**赛道上几乎无竞争**的位置。

证据：
- AIHawk（自动投递旗舰，29.6k 星）2026/4 被作者归档放弃
- LazyApply Trustpilot 拿 **2.1 星 / 52% 1 星**
- get_jobs（6.8k 星 Java）2024 底停摆
- 国内代投中介（卖课 8999-12999）正在被人民日报点名
- **国内市场没有任何成熟产品做投后追踪**——99% 学生用 Excel
- 全行业共识：自动投递 reply rate 1-3%，精投 reply rate 10-15%

定位本身值钱。

### ② SKILL 真有效果，输出质量在线 ✅

这是我打开 `examples/dogfood_w11_output.txt` 真跑数据看到的：

- **corpus_quality** 5/5 正确分类（marketer / offer_post / interview / project_share / other）
- **successful_profile** 给出 8 道**具体**面试题（反转链表 / Transformer attention √d 推导 / GRPO vs PPO / 1000 QPS agent inference pipeline 设计），每条带 evidence_count 和 uncertainty_notes
- **profile_resume_gap** 4 桶分类，"不能编"桶强制带验证渠道（学信网 / 背调）——这种诚实结构 ChatGPT 给不了
- **docx_tailor** 真把简历 9 段重写、保 docx 段落级 style（Times New Roman / size / bold 全保留）

**关键差异**：ChatGPT 给的是泛泛"建议复习算法 / 准备项目"，OfferGuide 给的是"10 天刷 leetcode hot100 重点 40 题（反转链表必练）+ 5 天写 attention √d 推导 blog"——**带数字、带动作、带证据归属**。

### ③ 产品壳烂、agent 体感像后台运维 ❌

UI 把"agent 的内部状态"当成了"产品的卖点"：home 页 13 个区块 / navbar 19 个 tab / 满屏「Mission Control / worldview / wake / trajectory / meta_reflect」——**这是 LangGraph 行话不是用户语言**。Claude Code / Manus / Devin 的首屏都是 1 个输入框，所有 internal state 在背景。

求职用户打开浏览器只想问一件事——「这家投不投 / 我下一步该干啥」——你的 home 没有秒答这个。

## 改造路线图

### 🔴 P0（这周 — 1.5 天工时）

- **删 .venv 死链 + 写 install.sh 1 行装** → 装机成功率 < 30% → > 80%
- **home 大瘦身（13→4 区块） + navbar（19→5 tab）**
- **术语去内核化**（Mission Control / wake / trajectory / worldview / meta_reflect 不暴露给求职者）
- **README 数字校准**（97% ATS 改成"海外 97% / 国内 60-70%"；字节"硬限 2"改成"建议而非硬限"）

### 🟠 P1（接下来 2 周 — 5-8 天工时）

- **Hero 评估 JD 改 SSE 流式** → 4 阶段（读 JD → 比对画像 → 算评分 → 出建议）每阶段 < 5s 看到文字
- **Onboarding flow 5 分钟**（强制：上传简历 + 选目标 + 选 5 个偏好公司，agent 第一次 wake 才有基础）
- **三档权限模式**（Auto / 重要操作问我 / 全 review，参考 Claude Code）
- **docx_tailor 提到 hero 旁** → home 加第 2 个 hero「上传简历 + 粘 JD → 9 段定向微调（保 Word 格式）」
- **失败 hand-off**（agent 卡住 → 红色 spinner + "我需要你帮忙：..." + 接管按钮把 trajectory 转成可编辑 markdown）

### 🟢 P2（一个月内 — 10+ 天工时）

- **正确修法 1**: tailor_resume 输出 `inserted_claims` + `prep_plan`（详见下方哲学修正）
- **正确修法 2**: 删 `COMPANY_APPLICATION_LIMITS` 硬编码、agent 自调研（详见下方哲学修正）
- **投后追踪信号源补强**（Boss 扩展 v2 / Gmail content script / 短信 paste-in 一线化）
- **corpus_collector 推到一线**（公司 N=0 时 1-click 触发）
- **GEPA 真活 + 砍 adapter 数量**（保留 2 个 SKILL 跑真活：score_match + prepare_interview，砍掉另外 3 个）
- **4 周 dogfood**：自己投 30 个 JD，把 [TBD-1..5] 5 个数填上

**总工时 ~ 2 周**做完 P0 + P1，4 周做完 P0+P1+P2。

## 两条哲学层面的修正（不是细节是思路）

我前份给的两条修法**思路错了**。用户反馈纠正后改写如下。

### 正确修法 1: tailor_resume 透明告知 + 学习引导

**原错思路**: keyword containment check，没在原文就 raise TailorViolation 拒绝下载——**工程师思维，把"编造"当 bug 拦死**。

**正确思路**: tailor 不是"产物"，是"学习清单的入口"。

数据结构改造——`InsertedClaim` 字段每条带：
- `source_kind`: `from_jd` / `supported_by_project` / `completely_new` ⚠
- `why_inserted`: "JD 第 4 条要求 + 字节 Agent 岗 4/5 面经问 retrieval miss debug"
- `prep_plan`: 5-7 天具体方案（读什么 paper / 跑什么 demo / 备 5 道高频题 / 万一被问没准备好怎么诚实兜底）

`prep_plan` schema **跟 profile_resume_gap 的"短期能补"桶完全一样**——直接复用。UI 上让用户逐条 review，保留的进 todo。

**为什么这个比 raise 好**：用户面试被问到 RAG 时**他真的会答**——5 天前读了 paper、跑了 demo、备了 5 道题。把简历微调从"虚假"变成"真学习"。这才是 OfferGuide 的卖点。

### 正确修法 2: compare_jobs 让 agent 自调研

**原错思路**: 给 hardcoded 表加 `source: "estimated"` 字段、UI 标"低置信度"——**律师思维，把不准当免责声明**。

**正确思路**: 一岗多投这种动态信息（每年政策变 / 不同 BG 限额不一样 / 网传 ≠ 实际）**永远不该 hardcoded**——让 agent 当场调研。

流程：删 `COMPANY_APPLICATION_LIMITS` 表，`effective_app_limit()` 改成
1. 本地 corpus 找 ≥3 条 2026/4 后的源 + briefs ≤7 天缓存 → 直接答
2. 不够 → Tavily 现搜 4 条（牛客 / 小红书 / 一亩三分地 / 公告）→ LLM 评每条来源时间/类型/部门差异
3. 综合答案 + 置信度 + 可点击来源列表
4. 入 briefs 表给后续用户复用

UI 上用户问"字节能投几个"看到的是 streaming「正在搜 4 个 2026 年源...」而不是 hardcoded 数字——**这件事 ChatGPT 做不到，OfferGuide 能做到**——真正的差异化。

`briefs.refresh_brief()` + `effective_app_limit()` 双轨架构 W8''''' 已经搭好——只是默认 fallback 到 hardcoded 而不是"我不知道，让我现搜"。**把那条 fallback 删掉就对了**。

### 元层面反思

我前份两条修法都是**"快速 patch 不出错"导向**：
- raise violation = 出错就拦 = 工程师思维
- 加 source 字段 = 不准就免责 = 律师思维

用户的反馈是**产品 / agent 思维**：
- 给用户透明 + 教育
- 让 agent 主动调研

**这是 OfferGuide 该有的产品哲学**——产品壳从"防御性"变成"主动性"。

## 对比基线 — "之前难用版" vs 现在

DEVLOG 的时间线说明很多事：

- **W1-W7**：骨架期。SKILL 输出粗糙——你之前说"难用没效果"很可能是这时期
- **W11**: corpus_quality + successful_profile + profile_resume_gap 加进来 → **第一次有 evidence-cited 输出**
- **W12**: docx_tailor + 4 层反编造 → **第一次能产出可用 docx**
- **W13-W15**: agent loop + 心跳 + worldview + Mission Control → **加在了 agent 内部认知层，对求职用户没感觉**

**判断**：W11+W12 是真实的功能跃迁，输出质量从那时候起就上来了。但 W13-W15 加的全是开发者视角的能力——SKILL 输出好 + 产品壳烂 = 用户根本看不到 SKILL 输出有多好。

你现在不是在做"难用没效果"的产品——你是在做"输出有效果但用户看不见"的产品。这是两个完全不同的修复路径。
